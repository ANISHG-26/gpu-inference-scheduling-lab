# Lesson stack compatibility gates

Research checkpoint: 2026-10-22. Sources below are upstream primary sources, checked on this date. This note records preparation and compatibility checks for Slurm and Triton; neither stack was installed or measured. The GKE version observed during separate inference validation is recorded below.

## Slurm lesson: evaluate Slinky first, deployment blocked

Use SchedMD's Slinky `slurm-operator` and matching Slurm chart as the candidate, ahead of custom packaging. The repository is actively maintained and publishes Helm charts and CRDs. The current stable operator package visible upstream is **1.2.1**, published about two weeks before this checkpoint; current `main` documents the 1.3 series and chart metadata includes 1.3.0-rc1, so do not use `main` or a prerelease as an implicit pin. When implementation resumes, select a mutually compatible operator, CRD, Slurm chart, and Slurm image set from a dated stable release, then pin image digests. Upstream's compatibility table says 1.2.x supports Kubernetes 1.35–1.37 and Slurm 25.11+; confirm the actual retained GKE cluster version against that table before selection.

The important security gate is the **worker**, not just the operator. Upstream issue #238 documents that the current `slurmd` worker builder unconditionally sets `privileged: true` and adds `BPF`, `NET_ADMIN`, `SYS_ADMIN`, and `SYS_NICE`; the issue says there is no supported chart/NodeSet override in v1.2.0. The same report says unprivileged `slurmd` cannot initialize Slurm cgroups because `/sys/fs/cgroup` is read-only in the container and the systemd/dbus path is unavailable. Do not adopt its proposed cgroup-disabled workaround as equivalent job isolation: that is a separate, intentionally weaker teaching mode and requires explicit design review. The operator and webhook themselves have configurable security contexts, but chart defaults are empty, and their chart defaults also leave CPU/memory requests and limits empty.

GKE COS is not an automatic compatibility pass. Google documents `writableCgroups` support only from GKE **1.34.1-gke.2541000**, with node recreation when the setting is applied. That offers a possible host cgroup path for child processes, but does not prove Slurm's expected systemd/dbus setup works inside the pod or satisfy the Slinky worker's privileged security context. Verify cluster mode, exact GKE/Kubernetes version, COS image, Pod Security admission policy, allowed capabilities/privilege, cgroup v2 controllers and mount behavior on a disposable node pool before considering deployment. Do not loosen policy or recreate the retained foundation as part of preparation.

Storage is also an explicit gate. The upstream reference chart enables `slurmctld` state-save PVC by default and requests the cluster default StorageClass; persistence can be disabled for tests, with documented loss of controller state on restart. Accounting adds MariaDB and its storage; omit accounting for the small lesson unless needed. The reference chart can create accounting, controller, login, REST API, and worker pods; its installation example shows a 3-container controller and a 2-container worker. Upstream provides no universal minimum resource requirement. Values default resources to `{}` and the NodeSet example reserves no CPU or memory unless configured, so there is no defensible total footprint yet. Use the exact minimal render recorded below to select image identities, set requests/limits, and calculate fit against measured node allocatable/headroom. Confirm default StorageClass/PVC lifecycle and session cleanup; PVCs may outlive chart uninstall.

Minimum next checks: (1) confirm the target GKE version, COS image, node allocatable and Pod Security policy for a Slurm session; (2) test the tagged worker's required privilege and cgroup/systemd behavior on a disposable matching node; (3) use the no-accounting, no-login render recorded below to set explicit requests/limits and budget image storage; (4) test PVC creation and teardown; (5) only then make a reviewed decision whether upstream privileges are acceptable or whether a deliberately weaker no-cgroups lesson is acceptable.

License provenance: the [Slinky operator's tagged v1.2.1 README](https://github.com/SlinkyProject/slurm-operator/blob/v1.2.1/README.md#license) identifies Apache-2.0, as does the [1.2.1 Slurm chart metadata](https://github.com/SlinkyProject/slurm-operator/blob/v1.2.1/helm/slurm/Chart.yaml). Slurm itself is separately licensed under GPL version 2 or later, with an OpenSSL linking exception subject to the conditions in individual source files; see the [26.05.3 `slurmd` source notice](https://github.com/SchedMD/slurm/blob/slurm-26-05-3-1/src/slurmd/slurmd/slurmd.c) and [Slurm COPYING](https://github.com/SchedMD/slurm/blob/slurm-26-05-3-1/COPYING). The Apache chart/operator license does not establish the licenses of its packaged Slurm binaries or other image components. Exact runtime image identities and their included license inventory remain unreviewed.

## Triton lesson: CPU path is supported; image and runtime gates remain

The current Triton Inference Server release is **2.73.0 / NGC container 26.09**. NVIDIA's compatibility table identifies the 26.09 release and its backend versions. The `26.09-py3` image is a candidate for Python backend; `26.09-py3-min` is the base in NVIDIA's documented general container composition flow, which currently excludes CPU-only customization. Candidate linux/amd64 manifest digests are resolved below. Final runtime image selection and digest pinning await the disk and runtime checks.

CPU inference is an upstream-supported target for x86 and ARM, and both Python and ONNX Runtime are supported backends. For an intentionally tiny first lesson, use a deterministic CPU Python model or a pinned small ONNX model; this teaches Triton's serving protocol and model repository, not GPU LLM inference. Python backend models include `model.py`; the backend must match the Triton release's Python ABI. The live Python backend documentation describes shared-memory IPC, a default 1 MiB region per model instance that can grow, and says Docker's default 64 MiB `/dev/shm` is often too small. Size Kubernetes `emptyDir: {medium: Memory}` for `/dev/shm` from the model instance/input needs, and verify the exact pod runs with the intended non-root UID, writable model/cache/temp paths, and no privileged access. For an ONNX lesson, validate the exact ONNX Runtime backend and model opset on the selected release.

Extracted image storage is not established for the `26.09-py3` or `26.09-py3-min` candidates. Their compressed registry layer sums are recorded below, but NVIDIA's visible compatibility table does not establish their extracted size (for example, its 10.57 GB figure describes the distinct 26.09 `vllm-python-py3` image). Do not transfer that number to `py3`. The lab's existing node boot disk is 30 GB; whether the selected image(s), layer extraction, models, system data and other pods fit is unverified. NVIDIA's general compose workflow can remove unused backend functionality, but CPU-only customization is unavailable in that documented flow and no composed image size was measured here.

Minimum next checks: (1) select Python or ONNX and a tiny pinned model, with its Python ABI/opset; (2) use the resolved candidate digest to measure pull/unpack disk use on the target COS node/runtime, including model and writable-layer headroom; (3) run on a CPU-only node using non-root settings, explicit writable paths and a sized `/dev/shm`, then check readiness and valid/invalid inference; (4) if a candidate does not fit, evaluate a supported alternative such as a CPU source build, measure it, and pin the final image digest. The current documented compose flow does not supply a CPU-only fallback. No Triton runtime measurement exists yet.

License provenance: the [Triton 2.73.0 server source license](https://github.com/triton-inference-server/server/blob/v2.73.0/LICENSE) is BSD-3-Clause. NVIDIA's [Triton SLA page](https://docs.nvidia.com/deeplearning/triton-inference-server/sla/index.html) also publishes source/binary redistribution terms, while the [NGC container catalog's License section](https://catalog.ngc.nvidia.com/orgs/nvidia/containers/tritonserver) explicitly makes pulling and using the container subject to NVIDIA's linked End User License Agreement and Product-Specific Terms. Record the selected container's included component licenses and notices before redistribution; the server source license alone does not establish the terms of the composed NGC image. No such image inventory review has been completed here.

## Exact package and registry follow-up

The official Slinky `slurm`, `slurm-operator`, and `slurm-operator-crds` **1.2.1** OCI charts were downloaded and rendered offline, without installation. A no-accounting/no-login render defines Controller, NodeSet and RestApi CRs; the expected initial workload is three pods with six app/init image slots, plus the operator. Controller persistence defaults to **4 GiB RWO** on the default StorageClass. Controller/worker/REST resource maps are empty, so the rendered chart supplies no defensible CPU/memory budget. The [tagged worker builder](https://github.com/SlinkyProject/slurm-operator/blob/v1.2.1/internal/builder/workerbuilder/worker_app.go) confirms `privileged: true` and BPF/NET_ADMIN/SYS_ADMIN/SYS_NICE in this release. The chart's default Slurm image tags and `alpine:latest` also need immutable image selection before activation. The default packaging does not pass the lab's baseline Pod Security policy.

Anonymous NVIDIA registry manifest queries confirmed these **candidate** linux/amd64 identities; no layers were pulled and no image was selected for deployment:

| 26.09 candidate | Platform manifest digest | Compressed layer bytes |
| --- | --- | ---: |
| `py3` | `sha256:1f08352ff9318894ca24bb36a532ad450b1289f7a6aeb163ae752a446c400fe6` | 9,043,508,064 (8.422 GiB) |
| `py3-min` | `sha256:f5531a5cf882043ef41f9acec837666e04911c13dea6de45b5a96bf115ed902e` | 6,471,444,248 (6.027 GiB) |

Compressed layer sums do **not** establish extracted/containerd disk fit or extraction headroom on a 30 GB boot disk. The release's Python backend uses Python 3.12; ONNX Runtime is listed as 1.30.0. NVIDIA's [compose guide](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/customization_guide/compose.html) explicitly says CPU-only containers are not yet available for customization. Selecting backends from the two NGC images does not establish a supported CPU-only minimal composition. A publisher-supported CPU source build is a separate evaluated option, not an implemented shortcut. Verify runtime, disk, shared memory and non-root behavior before final image selection.

The newly provisioned inference test node reported Kubernetes `v1.36.4-gke.1495002`, COS and containerd 2.2.7. That Kubernetes version is inside Slinky 1.2.x's declared matrix. It does not establish privileged admission, writable child cgroups/systemd behavior or resource fit; those Slurm gates remain blocked.

## Deployment decision

**Neither stack is ready to deploy.** Slinky remains blocked on accepting/testing worker privilege and cgroup behavior on the exact GKE COS version, plus assigning resources to the rendered minimal chart and validating storage. Triton's candidate manifest digests are resolved; final image selection remains blocked on measuring extracted disk/model footprint and validating non-root, shared-memory, and CPU backend operation. CPU-only composition is unavailable in the current documented flow. These are deployment blockers, not assumptions to fill with estimates.
